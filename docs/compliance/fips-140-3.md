# FIPS 140-3 (Cryptographic Module Certification)

## What it is

FIPS 140-3 is the current federal standard for cryptographic modules. It certifies **implementations** (not algorithms). A FIPS-compliant deployment MUST use a FIPS-certified cryptographic module for **all** cryptography that protects federal information.

Approved algorithms are enumerated in **FIPS 140-3 Annex A** (SP 800-140C). Approved random-number generators in **Annex C** (SP 800-140A).

## What JaiClaw contributes

JaiClaw uses **exclusively FIPS-approved algorithms** and provides a `FipsPostureStartupCheck` that verifies at runtime that only FIPS-certified providers are registered.

### Algorithms used by JaiClaw (all FIPS-approved)

| Purpose | Algorithm | JaiClaw call site | FIPS 140-3 Annex A ref |
|---|---|---|---|
| Field encryption | AES-GCM-256 (128-bit tag, 12-byte nonce) | `AesGcmFieldEncryptor.encrypt()` | Annex A §3.2 (SP 800-38D) |
| Audit-chain hash | SHA-256 | `HashChainedAuditLogger.hash()` | Annex A §3.4 (FIPS 180-4) |
| API-key comparison | Constant-time via `MessageDigest.isEqual()` | `ApiKeyAuthenticationFilter.authenticate()` | Annex A §3.4 |
| JWT signing | HMAC-SHA256 | `JwtTokenValidator.sign()` (via JJWT) | Annex A §3.4 (FIPS 198-1) |
| ECDH key agreement | EC P-256 (secp256r1) | `CryptoService.generateP256KeyPair()`, `keyAgreement()` | Annex A §5.6 (SP 800-56A Rev. 3) |
| ECDH key agreement (X25519) | X25519 / XDH | `CryptoService.generateX25519KeyPair()` | Annex A §5.6 (SP 800-186) |
| OAuth PKCE | SHA-256 | `PkceGenerator.challenge()` | Annex A §3.4 |
| SecureRandom | Java default DRBG | `ApiKeyProvider.generate()`, `AesGcmFieldEncryptor.nonce()` | Annex C (SP 800-90A) |
| Password hashing | *(not used)* | JaiClaw does not hash passwords — all auth is token-based (API key / JWT) | N/A |

### No non-FIPS algorithms in framework code

The following algorithms are **not** in JaiClaw's crypto surface:

- MD5 (deprecated) — grep confirms no `MessageDigest.getInstance("MD5")` calls
- SHA-1 (retired for signature use) — grep confirms no `SHA-1` calls in production paths
- 3DES — no `DESede`, no `TripleDES` calls
- RC4 — no `RC4` calls
- Blowfish — no `Blowfish` calls
- Custom crypto — no hand-rolled ciphers

## FIPS provider certification

JaiClaw's algorithms are all on the FIPS 140-3 approved list. Whether the **implementation** is FIPS-certified depends entirely on which JDK the operator runs and whether FIPS mode is enabled. Common integration paths:

### Path 1: BouncyCastle FIPS provider (BC-FIPS 2.x) — recommended

BC-FIPS is a FIPS 140-3 Level 1 validated cryptographic module. Drop it on the classpath, register it as a security provider, and all `Cipher.getInstance("AES/GCM/NoPadding")` calls route through the certified module without any JaiClaw code change.

```xml
<!-- Add to adopter's pom.xml -->
<dependency>
    <groupId>org.bouncycastle</groupId>
    <artifactId>bc-fips</artifactId>
    <version>2.0.0</version>  <!-- FIPS 140-3 validated -->
</dependency>
```

```java
// In your Spring @Configuration, register the provider at startup:
@PostConstruct
public void registerBcFips() {
    java.security.Security.insertProviderAt(new BouncyCastleFipsProvider(), 1);
}
```

Set `jaiclaw.compliance.effective.fips-enforced=true` (or use the `fips` profile) to have `FipsPostureStartupCheck` verify at boot that BC-FIPS is the highest-priority provider.

### Path 2: RHEL / Oracle Linux FIPS mode

The OS-level FIPS mode gates the JVM's crypto to FIPS-certified providers. Adopter enables it at deploy time:

```bash
# RHEL 9
sudo fips-mode-setup --enable
sudo reboot

# Verify:
fips-mode-setup --check
# Should print: "FIPS mode is enabled."
```

Under RHEL FIPS mode, the default JDK is patched to route all `Cipher.getInstance()` calls to the NSS FIPS module. No JaiClaw code change needed. Set `jaiclaw.compliance.effective.fips-enforced=true` for runtime verification.

### Path 3: Corretto / Zulu / Adoptium FIPS builds

Some JDK distributors ship FIPS-enabled builds:

- **Corretto FIPS** — AWS's FIPS-enabled Corretto (available in AWS GovCloud AMIs)
- **Azul Zulu FIPS** — Azul's FIPS-certified JDK build
- **Adoptium Temurin** — not FIPS-certified as of writing; use BC-FIPS on top

### Path 4: AWS GovCloud / Azure Government host

Many CSP-provided JVMs are pre-configured for FIPS mode. Verify with:

```bash
# Confirm the JVM is running with FIPS providers
jrunscript -e "print(java.security.Security.getProviders())"
# Should list only FIPS-approved providers
```

## `FipsPostureStartupCheck` (JaiClaw's runtime verification)

JaiClaw ships a startup check that verifies the effective JCE provider list matches an allowlist of FIPS-certified providers.

**Wiring:** Always constructed. `enforce()` returns early if `jaiclaw.compliance.effective.fips-enforced` is `false` (default). When `true`:

- Enumerates `java.security.Security.getProviders()`
- Checks each provider name against an allowlist: `BCFIPS`, `SunPKCS11-*` (when in FIPS mode), `SUN`, `SunEC`, `SunJSSE`, `SunJCE` (permitted only when the JVM runs under OS-level FIPS mode)
- Fails startup with `IllegalStateException` if a non-FIPS provider is registered AND `enforced=true`
- Logs the provider list at INFO otherwise for operator visibility

**Configuration:**

```yaml
# Via compliance profile (recommended)
jaiclaw:
  compliance:
    profile: fips  # or fedramp-moderate, which also enables it

# Or explicitly:
jaiclaw:
  compliance:
    fips-enforced: true
```

**File:** `core/jaiclaw-security/src/main/java/io/jaiclaw/security/FipsPostureStartupCheck.java`

## How to enable / disable

**Default:** off. `FipsPostureStartupCheck` bean is always constructed but returns early — zero runtime cost when idle.

**Enable — via profile (recommended):**
```yaml
jaiclaw:
  compliance:
    profile: fips              # only FIPS enforcement, nothing else
# OR
jaiclaw:
  compliance:
    profile: fedramp-moderate  # includes FIPS + other federal-baseline flags
```

**Enable — individual flag:**
```yaml
jaiclaw:
  compliance:
    fips-enforced: true
```

**When running under OS-level FIPS mode (RHEL / Corretto FIPS / Zulu FIPS):**
```yaml
jaiclaw:
  compliance:
    fips-enforced: true
    fips:
      trust-sun: true    # skip the strict provider-name allowlist;
                         # operator attests OS-level FIPS mode is active
```

**Disable / override:**
```yaml
jaiclaw:
  compliance:
    profile: fedramp-moderate
    fips-enforced: false   # bench deployment without FIPS — explicit override
```

**Fully off:**
```yaml
jaiclaw:
  compliance:
    profile: none    # (default) — check is inert
```

## What's adopter responsibility

- **Selecting the FIPS module** — BC-FIPS, RHEL FIPS mode, or a certified JDK build
- **Registering the provider** — via `Security.insertProviderAt()` in adopter code
- **Maintaining the FIPS module** — patching, cryptographic-module-transition planning (FIPS 140-2 → 140-3 was mandatory as of Sept 2026)
- **FIPS 140-3 certification of the deployed system** — CMVP (Cryptographic Module Validation Program) tracks module certifications, but the deployed system also needs an ATO
- **Key material management** — JaiClaw's `SecretsProvider` SPI receives keys; adopter provides the secure storage (HSM, AWS KMS, Azure Key Vault, HashiCorp Vault)

## What's out of scope

- **Certifying a new cryptographic module** — that's a NIST CMVP process, months of work
- **FIPS 140-3 Level 4 physical protection** — hardware-only
- **Custom algorithms** — JaiClaw uses only NIST-approved algorithms; adopters MUST NOT implement custom crypto in extension code

## How to verify

**Runtime verification:**
```bash
# Enable FIPS enforcement
JAICLAW_COMPLIANCE_PROFILE=fips \
    ./mvnw spring-boot:run -pl :jaiclaw-gateway-app

# Expected startup log:
# FipsPostureStartupCheck: FIPS enforcement enabled
# FipsPostureStartupCheck: registered providers: BCFIPS, SUN, SunEC, ...
# FipsPostureStartupCheck: verification passed (all providers FIPS-approved)

# If a non-FIPS provider is present, startup fails:
# IllegalStateException: FIPS enforcement enabled but non-FIPS provider registered:
#     BouncyCastleProvider (non-FIPS)
#   Remedy: remove the non-FIPS provider, or use BC-FIPS instead.
```

**Grep for crypto call sites (audit trail):**
```bash
# Every Cipher.getInstance call in the entire reactor
find . -name "*.java" -not -path "*/target/*" -exec grep -Hn "Cipher.getInstance\|KeyPairGenerator.getInstance\|MessageDigest.getInstance\|Mac.getInstance\|KeyAgreement.getInstance" {} \;

# Verify against the FIPS-approved list above — every algorithm should match
```

**Manual `fips-verify.sh` script:**
```bash
# JaiClaw ships a helper (in maven-central-deploy/ or an adopter's ops scripts)
# that dumps effective JCE providers at runtime
java -jar apps/jaiclaw-cli/target/jaiclaw-cli-*-exec.jar fips-verify
# Outputs the provider list + FIPS-approved status per algorithm used
```
