### Breaking changes (Boot 4 stack)

- **Spring AI 2.0 property renames** — `spring.ai.*.chat.options.model` → `spring.ai.*.chat.model` (44 YAML files rewritten). The `.options.` segment is gone across all Spring AI providers.
- **Jackson 3 namespace** — every `com.fasterxml.jackson.*` import moves to `tools.jackson.*`. Custom serializers ported. `FAIL_ON_NULL_FOR_PRIMITIVES` default flipped and must be explicitly disabled where old behavior is required (fixed in `PipelineYamlParser`).
- **Spring Shell 4 rewrite** — `@ShellComponent` / `@ShellMethod` / `@ShellOption` were removed at 4.0. Migrated to `@Command` / `@Option` across ~35 files. `jline-reader` is no longer a transitive dep — added explicitly in `jaiclaw-perplexity` + `jaiclaw-skill-creator`. Quarantined pending Shell-4 component-model re-implementation: `OnboardWizardOrchestrator` + 16 wizard step classes, `PromptCommands`, `JaiClawPromptProvider`, `JaiClawShellPromptAutoConfiguration`, `YamlConfigWriter`.
- **`RestTemplate` → `RestClient` across channel adapters** — Discord, Slack, Signal, SMS, Teams adapters now take an HTTP-abstraction interface primary constructor (`SignalHttpClient`, `SmsHttpClient`, `DiscordHttpClient`, `SlackHttpClient`, `TeamsHttpClient`). Legacy `(…, RestTemplate)` constructors kept with `@Deprecated(since="1.0.0", forRemoval=true)` — they'll be removed at 1.1.
- **Spring Boot starter renames** — `spring-boot-starter-web` → `spring-boot-starter-webmvc` across 42 poms per Boot 4.
- **`EnvironmentPostProcessor` package move** — `org.springframework.boot.env.EnvironmentPostProcessor` → `org.springframework.boot.EnvironmentPostProcessor` in the 3 EPP classes (Banner, Secrets, Compliance) + both `spring.factories` key names.
- **`RestClientCustomizer` package move** — `org.springframework.boot.web.client.RestClientCustomizer` → `org.springframework.boot.restclient.RestClientCustomizer` in `JaiClawHttpAutoConfiguration`. `jaiclaw-spring-boot-starter` picks up `spring-boot-restclient` runtime.
- **Removed Spring AI starters** — `spring-ai-starter-model-oci-genai` (removed at 2.0 GA), `spring-ai-starter-model-minimax` (removed at 2.0 GA). `spring-ai-starter-model-vertex-ai-gemini` renamed to `spring-ai-starter-model-google-genai`. The `jaiclaw-starter-oci-genai`, `jaiclaw-starter-minimax`, and `jaiclaw-starter-vertex-ai` wrapper modules were deleted. MiniMax adopters route via the anthropic starter with `spring.ai.anthropic.base-url=https://api.minimax.io/anthropic`.
- **Spring State Machine kanban engine removed** — `jaiclaw-kanban` now ships only the default `TaskStateEngine` graph engine (7 files + pom dep dropped). SPI is unchanged.
- **`commons-logging` explicit dep** — Boot 4 / Spring 7 removed the `spring-jcl` drop-in. `jaiclaw-cli` and any fat-JAR consumer now needs `commons-logging` on the runtime classpath (bumped to 1.3.5).

### New / verified

- **`jaiclaw-web-errors-webflux` no longer crashes servlet-stack apps at boot** (`extensions/jaiclaw-web-errors-webflux`). Root cause: `JaiclawWebFluxErrorAutoConfiguration` gated on `@ConditionalOnClass(name = "org.springframework.web.server.WebExceptionHandler")` — a class present via `spring-web` on the servlet stack too (Spring 6 kept it available there). The autoconfig's `@Bean` method returns `JaiclawWebFluxErrorHandler`, which `implements ErrorWebExceptionHandler` from `spring-boot-webflux` — a class that is **not** on the servlet-stack classpath. Spring's `OnBeanCondition.getMethodReturnType` force-loaded the entire interface hierarchy while introspecting the bean method, dying with `NoClassDefFoundError: org/springframework/boot/webflux/error/ErrorWebExceptionHandler`. Fix: tighten the guard to `@ConditionalOnClass(name = "org.springframework.boot.webflux.error.ErrorWebExceptionHandler")` — same class the handler's return type actually implements, so the guard passing implies the introspection will succeed. Reactive-stack apps are unaffected (they already have `spring-boot-webflux` on the classpath). Servlet-stack apps that pulled the webflux jar transitively via `jaiclaw-spring-boot-starter` now boot cleanly with no `--spring.autoconfigure.exclude` workaround. Verified against the exact 2026-07-24 e2e sweep repro: `java -jar apps/jaiclaw-gateway-app/target/jaiclaw-gateway-app-*.jar --server.port=8080` (no exclude flag) — gateway binds port in 3s, no `NoClassDefFoundError` in the boot log. New Spock case `servlet-stack context without spring-boot-webflux does not load the autoconfig` in `JaiclawWebFluxErrorAutoConfigurationSpec` uses Boot's `FilteredClassLoader` to filter `ErrorWebExceptionHandler` and asserts the autoconfig is silently absent — first `FilteredClassLoader` test in the framework, sets a pattern for any future "missing-jar" autoconfig fixture. Module tests 10/10 green (7 in the autoconfig spec, up from 6). Starter pom edit to mark both `-mvc` + `-webflux` error-handler deps `<optional>true</optional>` was **deferred** — pre-flight check found no reactive-stack starter declares the webflux dep directly, so marking it optional would silently strip it from every consuming app. Annotation-only fix stands alone; the transitive-dep restructure is a separate ship.
- **New `render_response` framework tool + `RenderableTemplate` SPI + `object-rendering` skill** (`jaiclaw-ascii-render`, `jaiclaw-tools`, `jaiclaw-spring-boot-starter`). Ships the reusable version of what `jaiclaw-event-agent` spent multiple days iterating: a template registry + tool + profile helper + LLM-side fidelity rules that let apps render domain objects (event cards, task kanbans, ticket diffs, order summaries, …) as framed monospaced ASCII through reliable tool calls. **Five deliverables**: (1) `io.jaiclaw.asciirender.skill.RenderableTemplate` interface — 4-method SPI (`name`, `description`, `parameterNames`, `render`) that apps implement once per domain shape and register as Spring `@Bean`s. (2) `RenderableTemplateRegistry` — first-writer-wins by name, LinkedHashMap insertion order, WARN on collision + blank-name skip. (3) `RenderResponseTool` in `jaiclaw-tools/builtin/render/` extending `AbstractBuiltinTool`; builds its JSON schema dynamically from the registry's `names()` + `unionParameterNames()`; dispatches LLM calls to the right template; catches thrown exceptions and surfaces them as `ToolResult.Error` rather than crashing the tool call (matches the SPI's "should never throw" contract with a safety net). Logs entry/exit per call so operators can distinguish the three lookalike failure modes documented in the event-agent saga. (4) `SceneSpecHelpers.activeWidth(min, max)` — lifted from `jaiclaw-event-agent`, clamps the active `AsciiRenderProfiles.defaultProfile().width()` to the template's tolerances so `jaiclaw.ascii.default-profile: telegram_mobile` reroutes every registered template's layout with no code change. (5) `object-rendering` bundled skill at `core/jaiclaw-ascii-render/src/main/resources/skills/object-rendering/SKILL.md` with `alwaysInclude: true` frontmatter — auto-splices into every agent's system prompt when `jaiclaw-ascii-render` is on the classpath (which it is transitively via `jaiclaw-tools`). Ships the **four fidelity rules** (knowledge-gap framing, naming-as-forgery, byte-for-byte + no-strip-borders, verbatim-only reply) that make LLMs actually call the tool + paste output unchanged, plus the "what did NOT work" learnings (soft normative language, WRONG/RIGHT examples, listing the tool name repeatedly). New `RenderableTemplatesAutoConfiguration` in the starter (registered via `AutoConfiguration.imports`) wires the registry + tool from `ObjectProvider<RenderableTemplate>` beans; gated by `@ConditionalOnClass(RenderableTemplate.class)` + `@ConditionalOnProperty(jaiclaw.tools.render-response.enabled, matchIfMissing=true)`. Empty-registry case: schema has `enum: []` and the tool errors on every call with "no templates registered" — functionally identical to opt-out. **Testing**: 6 Spock cases in `RenderableTemplateRegistrySpec` + 4 in `SceneSpecHelpersSpec` + 4 in `RenderResponseToolSpec` (empty registry, dispatch, unknown template, template-throws safety net) + 6 in `RenderableTemplatesAutoConfigurationSpec` (metadata lock) + 1 in `ObjectRenderingSkillDiscoverySpec` (SkillLoader discovers the bundled skill from ascii-render's resources + carries all 4 fidelity rules). Ascii-render 127/127, tools 231/231, starter 79/79 — all green. Unblocks the migration path from `jaiclaw-event-agent`'s locally-forked `ResponseTemplate` + `ResponseTemplateRegistry` + `RenderResponseTool` + per-app fidelity rules — the app can drop ~200 LOC and every future rendering-fidelity bug becomes a framework bug fixed once.
- **Pipeline Studio stylesheet is now shadow-DOM-compatible + theme-aware + WCAG-AA** (`apps/jaiclaw-pipeline-studio`). Prior to this fix, `frontend/src/styles/app.css` had three overlapping problems: (1) `:root { --bg: … }` + `html, body, #root { height: 100vh; overflow: hidden; background: var(--bg) }` leaked into any host document that imported the CSS, flipping the outer SPA to dark and locking global scroll; (2) shadow-DOM adopters (using `react-shadow` to isolate the Studio) got invisible white-on-white rendering because `:root` matches nothing inside a shadow root and `html`/`body`/`#root` don't exist there; (3) the hardcoded dark palette had no path for adopters with a Light/Dark/System theme picker to make the Studio follow the outer theme. TapCRM hit all three while embedding the Studio at `/workflows/studio` in the clients SPA and had to maintain a locally-forked `studio.css`. Palette is now **light by default** with a dark override under `[data-theme='dark']` (targeting both `:host-context([data-theme='dark'])`, `[data-theme='dark'] :host`, and `:root[data-theme='dark']` so any placement works) + a `@media (prefers-color-scheme: dark)` fallback for browsers without an explicit theme. `--text-dim` bumped from `#94a3b8` (3.4:1 contrast on `--panel: #1e293b` — failed WCAG AA) to `#cbd5e1` in the dark palette (~7:1, passes AAA) and `#475569` in the light palette (~8.6:1 on `--panel: #f8fafc`). Skipped: renaming generic tokens to `--studio-*` prefix (Fix 3 from the issue) — breaking change for anyone already overriding `--accent` / `--bg`; deferred until an adopter reports a collision. New `test/styleContract.test.ts` (7 Vitest lock assertions) prevents regression — verifies the compound selectors are present, `100vh` doesn't reappear, both dark hooks exist, the WCAG-failing color doesn't reappear, `:host { display: block }` stays. Vite 6 production build clean (CSS bundle 19.67 KB → 20.29 KB for the new theme blocks). `@types/node` added at test-scope so the new spec's `fs.readFileSync` type-checks under `tsc --noEmit`. Java-side `PipelineStudioSpaAutoConfigurationSpec` (3 cases) stays green — untouched. **Adopter recipe** (per the deleted issue's verification section): TapCRM can now drop `taptech-web/apps/clients/src/pages/workflows/studio/styles/studio.css` and mount via `<react-shadow.div><style>{cssText}</style><StudioApp/></react-shadow.div>` with `<html data-theme='light'>` (or `dark`) on the outer host controlling the Studio's palette — no fork, no diverging theme.
- **Multi-provider ChatModel selection actually works** (`jaiclaw-spring-boot-starter`, `jaiclaw-examples/multi-provider-toggle`). Adopters shipping more than one Spring AI provider starter (e.g., `spring-ai-starter-model-openai` AND `spring-ai-starter-model-anthropic`) so they could flip providers at deploy time used to crash Spring Boot 4 at startup with `No qualifying bean of type ChatModel`. Root cause: Spring AI's provider auto-configs are gated with `@ConditionalOnProperty(name="spring.ai.model.chat", ..., matchIfMissing=true)` — with the property unset, all providers on the classpath try to register their `ChatModel` beans and the autowire tripped ambiguously. JaiClaw's `jaiclaw.agent.agents.<id>.llm.provider` config field encouraged this shape but the framework didn't bridge it. Fix: `LlmProviderBridgeEnvironmentPostProcessor` runs at env-post-process time (before any autoconfig fires) and injects `spring.ai.model.chat=<provider>` derived from the default-agent's `llm.provider` field — or, when the default agent doesn't set one, from the first non-null provider across `jaiclaw.agent.agents.*.llm.provider` (multi-agent fallback-scan). Never overrides an explicit `spring.ai.model.chat` setting. Fail-fast: if two or more Spring AI provider starters are detected on the classpath AND neither a selector nor a bridge source is available, throws `IllegalStateException` at boot with a targeted message naming both properties an operator can set — infinitely better than the downstream `No qualifying bean` mystery. Detects seven Spring AI starters (`openai`, `anthropic`, `ollama`, `google-genai`, `bedrock-converse`, `deepseek`, `mistralai`). **Four layers of testing**: 7 Spock unit cases against a stub classloader; 3 Spock integration cases that boot real Spring contexts with both starters on the classpath; a new fixture app at `jaiclaw-examples/multi-provider-toggle` (`MultiProviderToggleApp`) that boots + emits a `MPT-BOOT-OK selector=<x> chat-model-class=<fqn>` marker line + exits; and a new e2e-test Scenario 7 that drives the fixture through 4 sub-scenarios (bridge fires, fail-fast, explicit override, multi-agent fallback). All 72 starter specs green. Registered via `META-INF/spring.factories` at `Ordered.HIGHEST_PRECEDENCE + 20` (after `SecretsEnvironmentPostProcessor` so secret-backed provider names resolve first). Unblocks `jaiclaw-event-agent`'s multi-provider toggle — the app can drop the `@Bean(name="chatChatModel") @Primary @ConditionalOnProperty` workaround for the base "which starter fires" concern (the per-role qualifier pattern in `MultiModelConfig.java` remains for its own reason).

- **`JaiClawSecurityProperties` YAML binding actually works** (silent P1 fix). The `api-key-filter.skip-paths` feature added earlier in this cycle was **functionally dead when configured via YAML** — TapCRM discovered this in production trying `jaiclaw.security.api-key-filter.skip-paths: [/custom-bypass/**]` and finding every request still saw only the record defaults. Root cause: Spring Boot 4's `@ConfigurationProperties` record binder heuristically picked a delegating overload constructor instead of the `@ConstructorBinding`-annotated canonical one, and the delegate stuffed hardcoded defaults into fields it didn't take — nested `apiKeyFilter` / `rateLimit` records silently lost YAML values with no warning or exception. Fix: **every delegating overload constructor + every no-arg convenience constructor on `@ConfigurationProperties` records in this file is now `private`**, forcing the binder to the canonical form. Callers that need a programmatic default use a new `ApiKeyFilterProperties.defaults()` / `RateLimitProperties.defaults()` static factory — same pre-fix behavior, but not visible to the binder's overload-picking heuristic. Two new regression Spock cases (`yaml override of api-key-filter.skip-paths round-trips` + `yaml override of rate-limit.skip-paths round-trips`) boot Spring's `Binder` against a `MapConfigurationPropertySource` and assert the YAML value survives to `props.apiKeyFilter().skipPaths()` / `props.rateLimit().skipPaths()`. Two obsolete "backward-compat overload defaults" cases removed (their premise vanished with the private-overload change). All 88 module specs green. Repo-wide grep confirms zero external callers of the now-private overloads — the affected downstream apps (TapCRM) construct the record via `@Autowired`, never directly. Unblocks TapCRM's `AgentSecurityConfig.java:161` — the hardcoded skip-path list can be dropped in favor of `jaiclawSecurityProperties.apiKeyFilter().skipPaths()` on the next TapCRM release.

- **`ApiKeyAuthenticationFilter` + `RateLimitFilter` skip-lists are now configurable** (`jaiclaw-security`). Prior releases hard-coded the filter skip-lists (`/api/health` + `/webhook/**` for the API-key filter; only `/api/**` was rate-limited). Downstream apps mixing an API-key surface (`/api/**`, `/mcp/**`) with a browser OIDC surface (`oauth2Login()`) on the same host could not cleanly opt browser-navigation paths out of the API-key check — the filter runs before Spring Security's `FilterChainProxy` and 401'd browser requests before the OIDC chain got a chance to redirect. Two new property paths close the gap: `jaiclaw.security.api-key-filter.skip-paths` (defaults to `[/api/health, /webhook/**]` — preserves prior runtime behavior) and `jaiclaw.security.rate-limit.skip-paths` (defaults to `[]`; layers *additional* exclusions on top of the existing `/api/**` whitelist gate). Both filters now match paths via Spring's `PathPattern` (built-in `**` / `*` semantics) — Spring Security 7.x removed the legacy `AntPathRequestMatcher`. 12 new Spock cases (3 in `ApiKeyAuthenticationFilterSpec`, 2 in `RateLimitFilterSpec`, 7 in `JaiClawSecurityPropertiesSpec`); all 88 module specs green. ## 0.4.0

Released 2026-05-18.

### New Features

- **Pluggable Telegram HTTP Client** — `TelegramAdapter` now accepts an injectable `TelegramHttpClient` interface instead of using a hardcoded `RestTemplate`. The default implementation (`DefaultTelegramHttpClient`) uses JDK `HttpClient` with proxy support via `ProxyAwareHttpClientFactory`. Custom implementations can be provided as Spring beans.

- **Pluggable Telegram Polling Strategy** — A new `TelegramPollingStrategy` interface allows replacing the built-in `getUpdates` polling loop. The framework ships a `CamelTelegramPollingStrategy` that uses Apache Camel's Telegram component for polling, which is auto-configured by `CamelPollingAutoConfiguration` when Camel is on the classpath.

- **Gateway Message Filter Framework** — New `GatewayMessageFilter` interface in `jaiclaw-gateway` allows inserting message filters between channel adapters and `GatewayService`. When a filter bean is present, `FilteredGatewayLifecycle` is used instead of the default `GatewayLifecycle`. `TelegramUserIdFilter` now implements this interface for defense-in-depth user authorization and rate limiting.

- **Tools Configuration Environment Fallback** — Added `resolveToolsFromEnvironment()` in `JaiClawAutoConfiguration` to work around Spring Boot's silent failure when binding deeply nested records inside `Map<String, Record>`. The `jaiclaw.agent.agents.{name}.tools.profile` property is now read directly from the `Environment` as a fallback, following the same pattern used for `llmOverride` and `loopDelegateOverride`.

- **Telegram Markdown Fallback** — `TelegramAdapter.sendText()` now catches Telegram API "can't parse entities" errors and retries the message without `parse_mode`, ensuring delivery even when LLM responses contain malformed Markdown.

- **Empty Attachment Guards** — `TelegramAdapter.extractAttachments()` now checks `!fileId.isBlank()` before attempting downloads for document, photo, video, audio, and voice attachments. This prevents spurious 400 errors from Camel's `IncomingMessage` serialization which includes empty attachment objects.

### Changes

- **AgentRuntime Thread Pool** — `AgentRuntime` now uses a bounded virtual thread executor instead of an unbounded cached thread pool, preventing thread starvation under load.

- **TenantAgentRuntimeFactory Logging** — Added INFO-level logging for tool resolution, showing profile, registry size, resolved tool count, and tool names per tenant. Useful for diagnosing tool visibility issues.

- **SkillLoader JAR FileSystem Fix** — Fixed `SkillLoader` to handle JAR-based `FileSystem` instances correctly when scanning bundled skills from classpath resources.
